## 3. Screen-by-Screen Architectural Design Decisions

### 3.1 Screen W102 — Create Service Provider Account (Staff Workspace)
1. **Layout Grid:** 65% / 35% two-column structure replaces the previous narrow 500px card floating in whitespace:
   - **Left Column (65%):** The official SRS form fields grouped into logical fieldsets: Full Name, Business Name, Category, Email Address, Phone Number, and Linked Points of Interest (POIs).
   - **Right Column (35%):** Contextual Operational Guidance panel detailing staff provisioning authority, temporary password dispatch protocols, mandatory first-time password rotation, and audit logging.
2. **POI Multi-Select Component:** Replaced the previous single hardcoded checkbox with a reusable `SearchableMultiSelect` component displaying:
   - POI Name (e.g. *Hội An Riverside Heritage Resort*).
   - Unique POI Identifier (`POI-DANANG-0042`).
   - Category Badge (*Hotel* / *Commercial Lodging*).
   - Physical Address (*188 Cua Dai, Cam Chau, Hoi An*).
   - Operational Status indicator (*Active*).
3. **Password & Credential Security:** Strict adherence to SRS §3.9.1.5:
   - No password input fields appear in the form.
   - The temporary password is never displayed on screen to the Staff member.
   - It is generated by the backend and dispatched directly to the registered email address.
4. **Unsupported Fields Excluded:** Tax code, business registration certificate uploads, website URLs, and extra address lines are strictly omitted as they are not defined in the original Report 3.

### 3.2 Screen W103 — Service Booking Requests (Service Provider Workspace)
1. **Full-Width Table Density:** The table expands across the entire workspace container with fixed, balanced column widths to ensure zero horizontal text jitter:
   - `Request Code` (140px, monospace, bold ink).
   - `Service` (180px, clamped to 1 line).
   - `Option` (170px, clamped to 1 line, muted ink).
   - `Requested Date` (110px, `dd/MM/yyyy`, `white-space: nowrap`).
   - `Requested Time` (80px, `HH:mm`, `white-space: nowrap`).
   - `Quantity` (75px, centered).
   - `Traveler Name` (160px, guest name + contact phone in monospace).
   - `Status` (130px, semantic color-coded status badge with standard icon).
   - `Submitted At` (120px, `dd/MM/yyyy HH:mm`, tabular figures).
   - `Actions` (95px, right-aligned link button).
2. **Filter & Search Execution:**
   - Filters: Status (`CustomSelect`), Date Range (From/To pickers), and Keyword search.
   - Execution behavior: Search triggers exclusively upon clicking the **Search** button or pressing `Enter`, not on every keystroke, preventing race conditions and UI flickering.
3. **Representative Demo Dataset:** Populated with 10 representative bookings covering diverse Central Vietnam properties (Hoi An, Da Nang, Hue), varying room types, and all core SRS states (`Pending Confirmation`, `Confirmed`, `Completed`, `No-show`, `Rejected`, `Cancelled`).
4. **Sort Direction Ambiguity Resolution:** Pending Confirmation requests are grouped first. Secondary sorting defaults to Ascending check-in date (`dd/MM/yyyy`) to prioritize immediate guest arrivals, with the ambiguity explicitly recorded.

### 3.3 Screen W104 — Request Details & Operational Outcome (Service Provider Workspace)
1. **Asymmetric 62% / 38% Two-Column Architecture:**
   - **Left Column (62%):** Comprehensive reservation parameters (Request Code, Service, Room Option, Check-in Date/Time, Quantity, Estimated Total) and Contextual Operational Action Zones.
   - **Right Column (38%):** Traveler Identity block (Full Name, Monospace Phone, Email, Special Requests) and Direct Payment Notice.
2. **Strict State-Dependent Action Surfaces:**
   - **Pending Confirmation State:** Primary *Confirm Request* button (opens CR-05 modal) and secondary *Reject Request* button (opens mandatory free-text rejection modal).
   - **Confirmed State (Future Date):** Read-only confirmation status. Outcome recording actions are disabled and hidden until the stay date arrives.
   - **Confirmed State (Stay Date Reached / Passed):** Exposes the *Record Service Outcome* area: Actual Amount input (> 0 required for completion), live commission preview, *Complete Stay* button, and *Mark No-Show* button (with confirmation modal).
   - **Terminal States (Rejected, Completed, No-Show, Cancelled):** Read-only immutable outcome card displaying recorded timestamps and notes. No duplicate decisions permitted.
3. **Rejection Modal Policy:** Free-text textarea strictly validated with MSG123 ("Rejection reason cannot be blank"). No artificial pre-set categories are forced upon the receptionist.
4. **Direct Hotel Payment Enforcement (BR-196):** Prominent notice communicates that traveler pays the hotel directly upon check-in; TripMate collects no funds and processes no booking refunds.

### 3.4 Screen W105 — Commission Statements & Payment Reporting (Service Provider Workspace)
1. **Master-Detail Financial Ledger:**
   - Left side (60%): Statement ledger table displaying Period, Completed Bookings count, Total Actual Revenue, Commission Amount, Due Date, and Status.
   - Right side (40%): Selected Statement Detail card and Bank Payment Reporting workstation.
2. **Payment Reporting Workflow:**
   - Hotel receptionist/manager inputs the wire transfer reference code (`VCB-20261205-982341`) and clicks *Report Payment*.
   - Status updates immediately to **Payment Reported** (`Đã báo thanh toán`). It does *not* become **Paid** until Staff verifies receipt.
3. **Demo Account Clarity:** Bank beneficiary information is displayed inside a highlighted container clearly stamped **DEMO / Illustrative Data Only**, avoiding legal misrepresentation during evaluations.
4. **Removal of Hardcoded Assumptions:** Removed hardcoded "(10%)" from table headers and replaced fixed 7-day deadlines with dynamic statement due dates.

### 3.5 Screen W106 — Commission Reconciliation (Staff Workspace)
1. **Full-Width Reconciliation Workstation:**
   - Filter bar: Service Provider (`CustomSelect`), Period (`CustomSelect`), Status (`CustomSelect`), and Reference Search input.
   - Data Table: Service Provider name & POI ID, Period, Commission Amount, Due Date, Status badge, Monospace Bank Reference, Reported Timestamp, and Reconciliation Action button.
2. **Receipt Verification Workflow (UC-83):**
   - The *Record Receipt* action is enabled for statements in `Payment Reported` status.
   - Clicking triggers a CR-05 Confirmation Modal explicitly stating the provider, period, and full commission amount credited.
   - Upon confirmation: Status transitions to **Paid**, records acting Staff ID, logs timestamp in `Asia/Ho_Chi_Minh` (CR-07), and records an immutable audit entry under BR-174.

## 5. Unresolved Requirement Ambiguities

1. **W103 Secondary Sort Direction:** The canonical SRS mandates that requests in `Pending Confirmation` status appear first, but does not define secondary ordering for equal statuses.
   - *Design Resolution:* Secondary sort defaults to **Ascending Requested Check-in Date** (`dd/MM/yyyy`) so hotel front desk staff immediately see today's and upcoming urgent check-ins at the top of the queue.
2. **W105 Statement Period Granularity:** The SRS describes monthly commission statements, but does not specify whether partial-month or ad-hoc statement generation is permitted.
   - *Design Resolution:* Statements are presented on a clean calendar-month cadence (`01/MM/yyyy - LastDay/MM/yyyy`) with explicit day-range sub-labels.

## 6. Language, Common Requirements & Verification Audit

### 6.1 Canonical SRS Common Requirements Verification
In strict compliance with the original canonical SRS Report 3, the approved system Common Requirements codes are:
- **CR-01 (Pagination):** 20 records per page by default, preserved filter and sort parameters across page reloads.
- **CR-05 (Confirmation Dialogs):** Mandatory modal confirmation before executing irreversible or destructive business actions.
- **CR-06 (Toast Notifications):** Transient non-blocking notifications confirming asynchronous completion of actions.
- **CR-07 (Date & Time Formatting):** All timestamps and dates displayed in `dd/MM/yyyy` format in `Asia/Ho_Chi_Minh` timezone (UTC+7).

> [!NOTE]
> **Governance Finding on "CR-09":** Previous working notes referenced "CR-09" as a language requirement code. Direct inspection of the canonical Report 3 document confirms that no "CR-09" exists. The English user interface requirement is specified directly under **§5.2 Common Requirements** text. Design documentation has been re-baselined to reference SRS §5.2 directly to preserve strict requirements integrity.

### 6.2 Language Implementation & Requirements Mismatch
- **Web Administration & Provider Workspace (W102–W106):** 100% English UI text in compliance with SRS §5.2.
- **Traveler Mobile Application (M74–M75):** Retains approved Vietnamese localized microcopy. Recorded as an **SRS MISMATCH** against §5.2 in the QA evaluation register; the visual design is preserved without unauthorized modification pending product owner direction.
